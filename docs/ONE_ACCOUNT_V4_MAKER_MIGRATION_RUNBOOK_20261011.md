# Qwerty Plus — 单真实账号 V4 人工迁移操作手册

> 日期：2026-10-11。**本文件用于单用户的人工监督迁移，不是批量自动升级**。目标：将真实用户的本机 Legacy V1/V3 工作区安全迁到 S1 隔离 V4，再将原云端 V3 转为 V4。全程保留原账号不可变 userId；不重新注册。

## 上线约束

- 开发分支 `product/main`，Maker 对外发布分支 `master`。
- 生产构建的 `.env.production` 设
  `VITE_S1_ENABLE_EXPLICIT_V4_MIGRATION=true` 和
  `VITE_S2_ENABLE_UNIFIED_SYNC=true`，仅开放人工确认的网页入口。
- **V4 GA（2026-10-11 新版）**：服务端允许所有**有效认证账号**调用 V4 写入。原 `S2_SYNC_WRITE_ACCOUNT_IDS` 白名单已弃用，无需再配置。客户端必须为当前已登录的不可变 userId，服务端仍执行完整 V4、CAS、账号隔离校验。
- **不做 V3 自动迁移**：已有云端 V3 的普通 Sync 一律拦截；只有经两端备份和原 SHA/Revision 验证的显式高级恢复才可以升级。生产紧急停写可设置运行时 `S2_SYNC_WRITES_DISABLED=true`。
- GitHub Pages 不提供 Maker 云端同步；此手册只描述 EdgeOne 生产站人工旧账号迁移。
- 仅在用户确认备份、选择一个可信权威副本之后提交云端 V4。不要把“有 V4 备份文件”当成“已完成 S1 工作区迁移”。

## 用户执行前

1. **选数据最全的设备**作为主迁移设备（PC 优先）；暂停其他设备学习，并关闭同浏览器所有 Qwerty Plus 旧标签页。
2. 在该设备确认已登录**原有真实账号**，不要重新注册。若当前匿名，不要按本流程直接把空/匿名数据绑定为账号。
3. 打开 `https://qwerty-plus.edgeone.dev/`，进入 **设置 → 数据管理 → 本地备份 → 导出完整备份**，保存 `.gz`；紧接着使用 **验证 V4 备份文件（只读）**检查能通过、显示六张数据表。把备份复制到另一位置。
4. 若其他设备可能有尚未同步的进度，**先在那些设备单独导出 V4 备份**，不要假定云端已含全部记录。
5. 等 Maker 发布版本对应的生产构建生效。生产构建是否包含 S1/S2 标志可通过下方页面辨识；若出现“尚未在此部署启用”，先不要迁移或覆盖云端。

## Phase 1 — 本机归属 S1/V4，不改云端

1. 在**已登录原账号**的主设备打开：
   `https://qwerty-plus.edgeone.dev/?s1-migration=confirm`。
2. 页面必须显示 **S1 本机学习数据归属确认**，并明确写着 **账号 + 不可变账户 ID**；若显示“匿名工作区”、其他账号或无法识别的 ID，立即取消。
3. 核对原始 V4 本地备份已保存并完成只读检验，关闭同站旧标签页；勾选备份确认，点击 **确认归属并建立隔离工作区**。
4. 等页面完成事务并自动返回首页；不要中途强刷、清缓存或删除 IndexedDB。
5. 访问 `https://qwerty-plus.edgeone.dev/?s1-account=manage`，核对当前工作区是刚才的同一 **账户 ID**，复制该 ID（不需要复制 Token、密码或导出登录信息）。
6. 重新打开正常学习界面，检查词库/章节、Learning/FSRS 和历史统计未丢失。此阶段**还没有**将云端迁到 V4。

## Phase 2 — 确认 Maker 已部署 V4 GA

1. 确认 EdgeOne Maker 真实生产站部署的版本为本次 GA `master` 版本。访问 `/api/health`，验证 `capabilities` 包含 `backup-v4-authenticated-write-ga`；只看 GitHub 构建状态不够。
2. 无需配置账号白名单。可清理旧变量 `S2_SYNC_WRITE_ACCOUNT_IDS`；未清理也不影响本次 GA。
3. 仅在紧急事故发生时设置 Production 运行时 `S2_SYNC_WRITES_DISABLED=true` 暂停 V4 写入；解除时设置 `false` 或删除该变量。
4. 已有云端 V3 的真实账号**仍需继续 Phase 3 的人工显式迁移**。不允许直接点击普通 Sync 覆盖。


## Phase 3 — 云端 V3 → V4（需要确定保留哪一边）

1. 仅在主设备访问：
   `https://qwerty-plus.edgeone.dev/?s2-recovery=manage`。
2. 读取页面中的不可变账户 ID、云端格式、Revision 和 SHA。
3. 分别下载：**① 本地完整 Backup V4 (.gz)**、**② 云端原始 Backup V3 (.gz)**（云端若已 V4，则下载 V4）。两个文件都必须保存在独立目录，再勾选确认。
4. 判断哪个副本是权威数据：
   - **本机数据最全**：选择 **“保留本地 V4：覆盖云端当前 revision”**。这会把本机 V4 上传并替换原云端 V3。
   - **云端 V3 数据最全**：选择 **“保留云端 V3：显式转换为 V4，再恢复到本机”**。这会先安全升级云端，再以经过核验的云端快照恢复本机。
   - **两侧各有独有学习记录**：**不要选任何覆盖方向**。本项目不自动合并，必须先在离线备份层面明确取舍/合并方案。
5. 按页面要求**完整输入不可变账户 ID**，然后再次确认备份、Revision 和覆盖方向，点击继续。
6. 等云端 CAS 完成与页面恢复；若网络中断、出现 409/500 或不确定状态，**先重新读取云端 meta**，不要连续重新提交。
7. 再运行 `https://qwerty-plus.edgeone.dev/?s2-sync=run`，理想结果是本地/云端一致的 No-op；同时检查词库、已学习词/FSRS 状态和历史记录。

## Phase 4 — 其他设备、验证和旧版本退出

1. **每台其他设备先单独备份**，关闭旧标签页，使用原账号登录（注意：单会话设计，新设备登录会让前一设备 Token 失效）。
2. 逐台完成 S1 账户归属迁移；登录后保存并核对正确的不可变 userId。
3. 如其他设备本地已有未同步的独有数据，先人工比较其备份，不得直接用 Sync 覆盖。若它是空的/可放弃，使用受保护的 V4 Pull 获取刚迁好的云端数据。
4. 逐台核对六表、词库/章节、FSRS 状态、统计和自动/手动 Sync 的行为。仍有旧版页面缓存的设备不要进行旧 V1 上传；在已迁 V4 云端，服务器会返回 `409 sync_upgrade_required`。
5. 验证全部完成后，再安排 **停用 S1 Legacy V1 迁移入口**；保留 V4 备份的离线恢复能力和 V4 云端机制。不要在迁移当天删除历史备份。

## 失败回退原则

- 本地 S1 迁移失败：不要清理浏览器数据。旧版快照和 S1 Vault 是恢复依据；关闭多余标签页，按安全恢复页面处理。
- 云端 V4 CAS 成功但浏览器显示失败：先核验 **Revision + SHA + 账户 ID**，不得盲目重复 Push。
- 需要回退 Maker 代码：必须保持 **V4 感知、CAS 与 V1 写入降级保护**；优先使用新全局停写开关，不能回到允许 V1 覆盖 V4 的历史版本。
- 迁移过程中如遇“其他设备登录，当前登录被撤销”，先保留本地备份再确认退出，避免同时在多设备竞争迁移。

## 通过标准

主设备 S1 工作区 owner 为原 userId、Vault 原始学习数据保存；原云端 V3 按明确方向变为 V4，Revision + 原始 SHA/逻辑指纹可验证；任意旧 V1 客户端不可覆盖；S2 Sync 一次 No-op；原用户能继续 Learn/Typing；多设备不存在独有未同步数据遗失；备份文件仍保留。

**注意：**这是用户侧人工迁移 SOP，不代表助手已经代替用户在网页中完成生产数据迁移。
